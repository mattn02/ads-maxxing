# Campaign workflow integration verification

Engineering record; this is not the required author-written product note.

## Implemented boundaries

- A typed `generateCampaign` action persists an explicit request ID and direction before research. `continueCampaign` advances research, planning, generation, and review using the saved intent and existing stage checkpoints. Legacy sessions without that intent do not start paid work when opened.
- The public session derives a contextual next action. Safe continuation returns a successful session; a failure pauses until an explicit action. Unknown image outcomes require acknowledgement of the potential duplicate charge before a fresh paid attempt. Missing image-provider configuration fails before recording dispatch.
- Campaign membership is distinct from the active ad target. A campaign can include multiple products and exact variants; generation chooses one member with a verified reference while keeping the membership. Generating another member is one explicit ad request. Discovery coverage stays partial or unknown.
- Exact variant references require both observed product/variant membership and image ownership. A generic product photo does not establish a size, color, or phone option. Version 1 supports Shopify stores. Known product pages use their public Shopify Ajax JSON endpoint first, without a product HTML scrape or app installation. Firecrawl remains responsible for brand and collection discovery; unsupported stores receive an actionable setup error. The normal path uses structural product/variant ownership and the final original-versus-ad review rather than a broad optional six-photo classifier.
- `refineAd` records the feedback and creates an immutable child version. Current campaign scope is preserved. Compatible original/background/scene assets are reused; copy changes can render without another image request. An ad removed from the campaign must be included again before refining it.
- Human acceptance is stored separately from the automated verdict. It allows `pass` or `needs_human` only after a durable review with nonempty deterministic checks all passing. Re-review removes acceptance. This requires `supabase/migrations/202609220005_review_acceptance.sql` on the target database.

## Automated evidence

`tests/campaign-generation.test.ts` exercises the actual Workflow service with controlled providers and persistence reloads. It covers explicit authorization/idempotency, legacy behavior, planning retry, bounded requests, checkpoint reuse, uncertain paid outcomes, photo correction, multiple products, generic size/color variant references, refinement ancestry and stage reuse after active-target changes, and honest acceptance/re-review behavior.

The full test suite passed all 121 tests after Shopify-first integration and the reviewer truncation fix. The dedicated campaign and persistence recovery suites cover 16 cases, including a terminal-save SQL57014 failure through the actual repository functions: reloading without a durable research checkpoint exposes an explicit retry, not automatic repeated research. Unknown paid attempts also block research/target edits that could otherwise discard their checkpoints. The production build passed with `npm run build -- --webpack`, including TypeScript and route generation. Default Turbopack encountered a local subprocess port-binding `EPERM` while compiling CSS, both inside and outside the execution sandbox; the supported webpack build avoids that environment-specific limitation without a configuration change.

## Live verification limits

The prior real Loopy output and its immutable source/stage provenance are recorded in `real-ad-verification.md`. That production-service proof used one background and one scene request and recovered through a request boundary. It does not itself prove the new authenticated browser path. The user confirmed the hosted acceptance migration was applied successfully. Actual acceptance through the new browser journey remains to be verified.

The first ordinary browser run found three products and 12 exact variant members, but repeated large snapshot saves caused additional Supabase500 failures. Its completed research remains saved; no image request was dispatched during that run. The new source path produces compact Shopify sources. Older Shopify product sources are compacted before planning under a new immutable research ID, preserving their extracted facts and campaign scope. Hosted commit timing must be rechecked on this compact path. Large legacy research snapshots can still make commits slow. Omitting repeated historical research from each variant cut one measured payload from about 11.06 MB to about 5.54 MB, and subsequent saves succeeded. The original hosted SQL statement timeout's full cause is not established; no blanket mutation retry or timeout increase was added.

Read-only measurement of the paused browser campaign found 5,870,587 bytes before compacting its three Shopify product sources and 3,187,246 bytes afterward. All 12 members, three products, and 281 assets remained unchanged. Remaining legacy brand/collection HTML explains why the payload is still substantial; actual compact-save latency is tracked separately.

The resumed browser run saved the compact snapshot, planned a brief, and reached generation. A 3,197,142-byte `commit_campaign` request then failed with SQLSTATE `57014` after 11,199 ms. Logs and the awaited dispatch boundary establish that the failure was the background reservation save, before any new fal request; the outer failure save had incorrectly retained an in-memory attempted marker. That original record is preserved. Future failed reservation saves restore the pre-dispatch in-memory checkpoint before recording the error, and a regression verifies zero image calls and an explicit safe step retry.

The follow-up persistence change uses the new `commit_campaign_v2` RPC and requires migration `202609220006`. A request-local, bounded SHA256 map tracks research loaded or successfully saved by the server. Unchanged research is sent as `{researchReference:{id,schemaVersion}}`; unknown or changed data is sent in full through the existing immutable-snapshot guard. A missing v2 RPC fails with migration guidance and never falls back to an unsafe old write. Five local SQL harness runs passed, including the reference branch, owner/brand/schema checks, immutable full writes, role privileges, the complete acceptance matrix on v2 references, and existing persistence/onboarding/legacy approval behavior. The user confirmed migrations 005 and 006 were applied. The resumed hosted run then proved v2 reference saves at roughly 10–29 KB and 117–340 ms, with no new database failures. The original false attempted record remains intact.
